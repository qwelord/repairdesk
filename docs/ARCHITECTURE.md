# Архитектура RepairDesk

Три проекта разделяют предметную логику, хранение и интерфейс.

| Проект | Назначение |
|---|---|
| RepairDesk.Core | Модели, валидация, граф статусов, проверки совместимости, PBKDF2 |
| RepairDesk.Data | Параметризованные запросы MySqlConnector, транзакции, доступ по ролям, SQL-копия |
| RepairDesk.Desktop | WPF, формы, списки, печать, экспорт Excel, переносимый запуск MariaDB |

Слой представления использует обработчики пользовательских действий и WPF bindings. Изменение данных идет через Repository; SQL в коде интерфейса не размещается. Проект намеренно не добавляет REST API, контейнеры или сервер приложений для локальной защиты.

## Данные

14 таблиц: версия схемы, сотрудники, клиенты, заказы, комплектующие, услуги, позиции заказов, оплаты, события заказов, движения склада, игры, результаты тестов, предложения сборок и состав сборок. Связи обеспечены внешними ключами InnoDB. Физическое удаление заказов из пользовательского интерфейса не используется: отмена сохраняет аудит.

## Транзакции

При изменении заказа блокируется строка заказа и проверяется `version`. После успешного изменения версия увеличивается. Старая карточка получает понятный отказ вместо потери изменений другого сотрудника.

Добавление запчасти уменьшает остаток, создает позицию с фиксированной ценой и событие заказа в одной транзакции. Отрицательный остаток предотвращает условный UPDATE. Удаление позиции возвращает деталь. Отмена возвращает все детали и закрывает заказ одной транзакцией; отмена с невозвращенной оплатой запрещена.

Создание заказа из конфигуратора блокирует детали в порядке ID, списывает весь набор и добавляет услугу сборки. Если хотя бы одной детали не хватает, все изменения откатываются. Сохранение предложения склад не резервирует.

SQL-копия читает таблицы внутри транзакции REPEATABLE READ. Строки записываются в UTF-8 hex-литералах, что сохраняет кавычки, переводы строк и кириллицу. Восстановление проверяется в отдельной базе.

## Разграничение доступа

Пароли сотрудников хранятся как PBKDF2-SHA256, 210000 итераций, случайная соль, сравнение за постоянное время. Для новых записей соли создаются отдельно. Начальные демонстрационные учетные записи имеют один известный учебный пароль; их необходимо сменить для реального использования.

Ограничения ролей проверяются в Repository и правилах заказа, а не только отключением кнопок. Мастер видит назначенные ему заказы. Клиент приложения напрямую соединяется с БД: это локальная учебная архитектура, а не граница безопасности между недоверенными компьютерами. Для развертывания в организации потребуются отдельный сервер API, управление доступом к БД и аудит учетных записей сервера.

## Совместимость и FPS

Проверка использует структурированные характеристики локального каталога. Неизвестная версия BIOS всегда требует сверки. Мощность БП — инженерный ориентир с запасом, а не расчет реального энергопотребления.

FPS — опубликованные замеры по выбранному GPU и разрешению. Они не пересчитываются по произвольным коэффициентам процессора и не обещают производительность конкретного клиентского ПК. Версия игры, пресет, масштабирование и источник показываются рядом с результатом.
